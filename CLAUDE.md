# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A Vampire: The Masquerade 5th Edition MUD on **Evennia 6.x** (Django 6 + Twisted), Python 3.12+, managed with `uv`.

## Commands

The repo root is the Evennia game directory, so run everything from here. With the venv active use `evennia ...`; otherwise use `uv run evennia ...` (on Windows, `.venv\Scripts\evennia`).

```bash
uv sync                                   # install (incl. dev group)
evennia --initmissing                     # once per clone: creates server/conf/secret_settings.py + server/logs/
evennia migrate                           # first run, after model changes, and after every pull
evennia start                             # first start prompts for the superuser
evennia reload
evennia stop
evennia status
evennia makemigrations <app>              # bbs, jobs, status, boons, traits, builder

evennia test --settings settings.py .                              # all tests
evennia test --settings settings.py dice.tests                     # one module
evennia test --settings settings.py jobs.tests.CmdJobsTests.test_list_all_jobs   # one test

ruff check . && ruff format .             # also run by pre-commit (pre-commit run --all-files)
```

- `server/conf/settings.py` refuses to load (ImproperlyConfigured) if `server/conf/secret_settings.py` is missing or its `SECRET_KEY` is still Evennia's default. That applies to every `evennia` command, tests included, so run `evennia --initmissing` first in a fresh clone or worktree. `server/conf/secret_settings.example.py` documents the other per-host settings.
- The database is the single SQLite file `server/evennia.db3`. Back up by stopping the server and copying it.
- Web authority uses Evennia permission strings, not Django's `is_staff`: `web/permissions.has_perm(user, perm)` wraps `check_permstring` (superusers pass). The web builder requires `Builder` on the account (`perm *<account> = Builder`).
- Tests run through Evennia's Django runner (there is no pytest setup). Command tests must subclass `evennia.utils.test_resources.EvenniaCommandTest` to get `self.call` (its `msg` argument matches the *start* of the output; use the returned string with `assertIn` for fragments). A test directory is only discovered if every parent directory is a package, so keep the `__init__.py` files.
- The suite is green: `OK`, with no expected failures today. If you find a known bug you can't fix yet, write the correct-rule test and mark it `@unittest.expectedFailure` with a `# F-###, fixed in PR N` comment (the summary then reads `OK (expected failures=N)`). An unexpected success fails the run, so when you fix one of those bugs, remove its marker. Don't add tests that assert the current behaviour where it disagrees with the V5 core book; write the correct-rule test and mark it instead.
- Prefer real characters (`EvenniaTest`/`EvenniaCommandTest`) over `Mock` characters, and patch only the dice (`dice.dice_roller.randint`). Attributes come back as `_SaverDict`/`_SaverList`, so check `collections.abc.Mapping`, not `dict`.
- CI (`.github/workflows/tests.yml`) runs `uv sync --locked`, `uv run evennia --initmissing` and `uv run evennia test --settings settings.py .` on every push and pull request, then requires the runner's `OK` summary line. `evennia test` exits 0 when settings fail to load (for example, a missing `secret_settings.py`), so judge a run by its `OK`/`FAILED` line, not its exit code.
- Ports: telnet 6660, web **6665** (browser-facing; 5001 is internal), websocket 6662, AMP 6670. Per-host overrides and secrets go in `server/conf/secret_settings.py` (untracked).

## Architecture

**Import root.** Modules import relative to the repo root with no package prefix (`from dice import dice_roller`, `commands.command.Command`, `INSTALLED_APPS += ("bbs", "jobs", ...)`). Do not add a `beckonmu.` prefix. That directory was flattened into the root.

**Commands.** `COMMAND_DEFAULT_CLASS = "commands.command.Command"` is a `MuxCommand` subclass with styled error/usage helpers. Evennia's stock commands and the `jobs` commands inherit it; the other game commands subclass Evennia's `default_cmds.MuxCommand` (switches, `lhs`/`rhs`) or bare `evennia.Command`, which has no switch or `=` parsing and no styled helpers, so check a class's base before using `self.switches` or `self.styled_error()`. To make a command available, add it in `commands/default_cmdsets.py`. The cmdsets import lazily inside `at_cmdset_creation` and also merge the per-system cmdsets (`dice.cmdset.DiceCmdSet`, `bbs.commands.BBSCmdSet`, `jobs.cmdset.JobsCmdSet`, `commands.v5.blood_cmdset.BloodCmdSet`). V5 command classes in `commands/v5/*.py` are thin; the mechanics live in `commands/v5/utils/*_utils.py` and `dice/`. Every V5 d10 comes from `dice/dice_roller.py`: pools through `roll_v5_pool`/`roll_contested` (Hunger dice, criticals, messy criticals, bestial failures, `apply_willpower_reroll`), Rouse checks through `dice/rouse_checker.py`, both via `dice_roller.randint`, the one function tests patch. Commands report `RollResult`s; don't roll dice with `random` in command code (only `hunting_utils` uses `random`, for the resonance and complication tables). Unknown-command styling comes from `commands/system_commands.SystemNoMatch`. Evennia's `charcreate` is removed from `AccountCmdSet` (characters are created only on the website), and there is no in-game chargen. `@promote`/`@abandon` are gone; `@cleanup_sandbox` is a thin wrapper over the web builder's cleanup unit.

**Character state lives in Attributes, not models, behind `Character` accessors.** `typeclasses/characters.py` initializes (only if missing, via `attributes.has()`) one schema on `char.db`:
- `stats`: `attributes.{physical,social,mental}.<key>`, `skills.{physical,social,mental}.<key>`, `specialties.<skill_key> = ["Name", ...]` (a skill can hold several), `disciplines.<key> = {"level": n, "powers": ["Power Name", ...]}`; the `blood_sorcery` entry also holds `rituals` and the `thin_blood_alchemy` entry `formulas` (lists of names; `LEARNED_LISTS`). That is the only store of learned rituals and formulas: there is no `stats["rituals"]`/`stats["formulas"]`. Keys are lower_snake_case (`animal_ken`, `blood_sorcery`).
- `vampire`: `clan`, `generation`, `blood_potency`, `hunger`, `humanity`, `predator_type`, `age_category` (Sea of Time, set at creation), `current_resonance`/`resonance_intensity`/`resonance_expires`, and the accessor-backed `torpor` (`{reason, time}` or None; set by a failed `rouse/wake` at Hunger 5; staff see and end it with `+torpor`/`+torpor/end`, `commands/v5/staff.py`), `last_hunt` and `slake_carry`. It is the only store of clan, generation and predator type. Bane and compulsion are derived from the clan, not stored.
- `pools`: damage counters only, `{"health"|"willpower": {"superficial": n, "aggravated": n}}`. Maximums and current values are derived, never stored.
- `humanity_data` (convictions, touchstones, stains); `advantages`: `backgrounds` (`{key: dots}`, or for instanced backgrounds such as Allies `{key: [{"dots", "note"}, ...]}`), `merits`/`flaws` (`{"Canonical Name": dots}`), `notes` (`{"merits"|"flaws": {"Canonical Name": "note"}}`, e.g. a Linguistics language or a Clan Curse's clan); `experience` (`total_earned`, `total_spent`, `log`; unspent XP is derived); `active_effects`.

Read and write this through the accessors: `hunger` (0-5), `blood_potency` (0-10), `humanity` (0-10), `stains` (0-10), `generation` (4-16), `clan`/`predator_type` (canonical names from `v5_data`), `bane`/`compulsion` (read-only), `resonance` (dict or None; type must be in `RESONANCES`), `get_trait(name, category=None)`/`set_trait(name, value, category=None)` (attributes, skills, disciplines, single-rating backgrounds; names resolve case-insensitively through `world.v5_data.TRAIT_REGISTRY` and raise `UnknownTrait`/`WrongCategory`; values must be whole numbers in range), `background_instances()`/`set_background_instance(name, note, dots)`, `set_advantage("merits"|"flaws", name, dots, note=None)`/`advantage_note()`, `age_category`, `known_rituals`/`known_formulas`/`learn_ritual_or_formula(kind, name)` (with `rituals`/`formulas`/`learn_ritual()`/`learn_formula()` as aliases that read and write the same per-discipline lists, used by web chargen), `specialties`/`add_specialty()`/`remove_specialty()`, `convictions`/`add_conviction()`/`remove_conviction()`, `touchstones`/`add_touchstone()`/`remove_touchstone()`, `discipline_levels`, `known_powers`/`learn_power()`, `advantages`, `health_max` (Stamina + 3), `willpower_max` (Composure + Resolve), `damage`/`set_damage()`, `current_health`/`current_willpower`, `xp` (earned - spent)/`xp_earned`/`xp_spent`, `bio`, `is_approved` (reads `CharacterBio.status`; approval is stored nowhere else), and `reset_sheet()`/`snapshot_sheet()`/`restore_sheet()` (used by chargen resubmission). The remaining direct writers are `xp_utils` (the `experience` totals and log), `background_utils` (per-session `background_uses` counters), the effect helpers (`active_effects`). Web chargen (`world/rules_chargen.apply_chargen`) writes only through the accessors. There is no top-level `hunger`, `disciplines`, `resonance` or damage Attribute; don't add one. Two transient top-level Attributes exist: `blood_surge` (a readied Blood Surge; `commands/v5/utils/blood_utils.py`) and `pending_frenzy_test` (hunger frenzy tests owed after a Rouse past Hunger 5; `dice/rouse_checker.flag_hunger_frenzy` records them and the causing command rolls and clears them). A `splat` Attribute (`Character.splat`: `vampire` by default, `mortal` or `ghoul` (`SPLATS`), set by `+npc/create <name>=<splat>`, default mortal for NPCs) decides who rolls Hunger dice (`dice_hunger`) and halves Superficial damage, and the web builder's "Character Type" trigger condition reads it. XP purchases go through `Character.spend_xp`, which writes the trait, the XP total and the log together. `hasattr(obj.db, "x")` is always True in Evennia, so test with `obj.attributes.has("x")` or `obj.db.x is None`.

**One source of V5 rules data: `world/v5_data.py`.** Attributes, skills, clans, `DISCIPLINES` (with their powers, Blood Sorcery `rituals` and Thin-Blood Alchemy `formulas`) and the flat `DISCIPLINE_POWERS`/`find_power()` index, predator types, backgrounds, merits, flaws, Blood Potency (the errata'd table), generation tables, resonances and frenzy provocations live there, and game code imports them from there; don't hardcode a copy elsewhere (`tests/test_v5_data.py` checks for BP tables). The content follows the V5 core book with each table's source cited in a comment; values that couldn't be checked are marked `UNVERIFIED`. Non-core clans and disciplines sit in `NON_CORE_CLANS`/`NON_CORE_DISCIPLINES` and are not offered to players; web chargen rejects them, and a character stored with one gets no in-clan disciplines and can't buy disciplines until staff change its clan. A power's `rouse` is a Rouse-check count (0 = free), and its `duration` is a token from `DURATION_TYPES` (`duration_text` holds the book's wording). The creation distributions are the `CREATION_*` constants (owner sign-off pending). XP costs are `XP_COSTS`, and hunting grounds and feeding sources `HUNTING_GROUNDS`/`FEEDING_SOURCES`. There are no trait tables in the database; `/api/traits/` serves `v5_data` as JSON.

**Django apps.** `bbs`, `jobs`, `status`, `boons`, `traits` each follow the pattern `models.py` + `commands.py` (in-game) + `utils.py` + `migrations/` (`traits` has no in-game commands). `web/urls.py` mounts `web.website` (homepage, `/character-creation/`, `/staff/character-approval/`, and redirects that replace Evennia's stock `characters/create/` and `characters/update/` pages), `webclient`, `admin`, `api/traits/` (→ `traits.urls`), and `builder/`. `AUTO_CREATE_CHARACTER_WITH_ACCOUNT = False` and `MULTISESSION_MODE = 3`. `server/conf/at_server_startstop.at_server_start` calls `world/seed_defaults.seed_defaults()`, which creates whatever is missing of the default job buckets (`jobs.utils.DEFAULT_BUCKETS`; `Bucket.player_submit` marks Requests and Bugs as the ones players may `job/submit` to and list with `buckets`), the Camarilla positions (`status.utils.initialize_default_positions`) and the BBS boards the news names, and never changes existing rows.

**Web chargen is the only way to a player character.** The form (`web/templates/character_creation.html` + `web/static/chargen/codex-chargen.js`) reads the rules from `GET /api/traits/rules/` and posts `buildPayload()` to `/api/traits/character/create/`. On the server, `world/rules_chargen.py` is the one path: `parse_submission()` (fixed keys at every level, unknown keys rejected), `validate_v5_creation()` (pure, reads `v5_data`), and `apply_chargen()` (writes the same `Submission` through the accessors). `traits/utils.py` holds the units of work (create, approve, reject, revoke, resubmit); each runs wholly on the reactor via `web/main_thread.call_in_main_thread` and undoes itself with Evennia operations if it fails part-way (no DB rollback, no `transaction.atomic()` around it). `traits.CharacterBio` is the application: `account` is the only ownership fact (never `db_account`), `status` the only approval fact, changed only by `CharacterBio.transition()` (submitted→approved|rejected, rejected→submitted, approved→revoked, revoked→submitted; conditional update; records `reviewed_by`/`reviewed_at`). It also keeps the last `submission` to prefill the edit form; that is never read as the sheet (age, notes, rituals and formulas are on the character). A rejected application is resubmitted with a new sheet (`resubmit_unit` resets and rewrites it); a revoked character keeps its played sheet and XP and is resubmitted with narrative changes only (`resubmit_revoked_unit`). The only character cap is pending + approved applications against `MAX_NR_CHARACTERS` (`over_character_limit`; the unit uses `create_object`, not `Character.create`, so Evennia's slot check doesn't apply). Each application has an `Approval` job (`CharacterBio.job_id`) kept in step by the units and by `Character.at_object_delete`. `CharacterBio.applicant_ip`/`reviewer_ip` (validated with `ipaddress`, else None) let the staff page flag same-address reviews; they are shown to Builders only, never to the applicant. The flag is a hint, not a control (`reviewed_by` and the staff policy are): loopback addresses never match, and REMOTE_ADDR identifies the client only behind a trusted front proxy that overwrites `X-Forwarded-For`, with `UPSTREAM_IPS` set to that proxy (Evennia trusts the first X-Forwarded-For entry from any `UPSTREAM_IPS` peer, and the Portal adds none). The create unit re-checks the name and the cap on the reactor, because the view's checks alone race. Steps after a committed status change (notifications, job, unpuppeting) are best-effort and logged. Every `Character` gets `typeclasses.characters.CHARACTER_LOCKS` from `get_default_lockstring`/`basetype_setup` (which swaps them in with `locks.replace`) however it is created, and `traits` 0003 re-locked the characters that existed before: `puppet:(char_owner() and char_approved()) or perm(Admin)`, `delete:char_owner() or perm(Admin)`, `edit:perm(Admin)` (lockfuncs in `server/conf/lockfuncs.py`). So an unapproved character can't be puppeted, and with no puppet there is no `roll` or `+spend`. Authority is `web.permissions.has_perm`: Builders review others' applications, Admins may review their own (recorded), only Admins revoke (which unpuppets live sessions), and owners or Builders read a character. Approval moves the character to `START_LOCATION` and refuses if it doesn't exist. Staff NPCs are made with `+npc/create <name>[=<splat>]` (`commands/v5/staff.py`): no account, no `CharacterBio`, and `NPC_LOCKS` (puppet/edit/control/delete for Builders) in place of the gate. A plain `@create`d Character gets the player gate, and only Admins can change its locks. Owners may `chardelete` their own characters, approved ones included.

**Web builder** (`web/builder/`). A `BuildProject` stores a whole area as a JSON map blob with a status lifecycle. `sandbox_builder` creates real Evennia rooms/exits from that JSON. Review rules: Builders never approve or reject their own project (Admins and above may), and `reviewed_by`/`reviewed_at` are always recorded and listed on the review page. `map_data` saves (including `RoomTriggersAPI`) are allowed only in `draft` (a rejection returns a project to draft), and they need the current `version`. Approve/reject also need the `version` the reviewer saw and are conditional updates on `status=submitted` (409 if stale); submit and reject also bump `version`, so a card loaded before a resubmission goes stale. Owners may delete only drafts; Admins may delete any project except one with a sandbox (`has_sandbox()`: built, or `built_object_ids` set), which must be cleaned up first, on the web and in the Django admin. Django admin shows the review record and snapshot read-only. Submit requires a live `connection_room_id` + `connection_direction` (`validators.validate_connection`). Approval snapshots `{map_data, connection_room_id, connection_direction}` into `approved_map_data`, and the sandbox build reads only that snapshot. Build, cleanup and promote are owner-or-Admin. Submit (and the build, again) requires `validators.validate_build_map`: ids `^[A-Za-z0-9_-]{1,32}$`, the editor's enum values, exit locks limited to `traverse`/`view` with `all()`/`perm()`/`tag()`, every trigger valid, at most 100 rooms / 200 exits (what all three units handle in about a second on file-backed SQLite), at most 10 triggers per room and 30 timed triggers per project (interval ≥ 60 s), and no MXP link markup (`|lc`/`|lu`, `web/builder/markup.py`) in any builder text, because a clicked link runs a command as the clicker. The editor receives the map through `json_script`; never render builder data with `|safe` or into inline handlers. Because Django views run outside the game loop, every Evennia object mutation from web code must run on the reactor via `web/main_thread.call_in_main_thread` (decides per call; refuses inside `atomic()`). Build, promote and cleanup are each one unit of work that runs wholly on the reactor in autocommit and, on failure, undoes itself with Evennia operations (delete what it created, stop Scripts it started, restore tags), never `transaction.atomic()`: `sandbox_builder.build_unit` (no container room; the entry room is the room flagged `is_entry`, else the first; tags/Attributes are bulk-inserted; timed-trigger Scripts start last; every created id goes into `BuildProject.built_object_ids`), `promotion.promote_unit` (uses only the reviewed connection from `approved_map_data` and refuses a different one with 409; checks the direction is free at both ends; strips `sandbox`/`project_N` from the recorded objects and creates the two connecting exits last), and `sandbox_cleanup.cleanup_unit` (bulk: stops the area's Script timers, then deletes Scripts, Attributes and objects by queryset; loose items go home). Promotion untags in one query too. Tags are never authority for a destructive operation, because any Builder can forge them with `tag`: cleanup and promotion act only on recorded ids ∩ `project_N` + `sandbox` ∩ Room/Exit as recorded ∩ no account, and cleanup refuses while a character is inside, an unrecorded exit touches the sandbox, or a recorded object no longer matches. Cleanup's three callers (`builder/api/build/<pk>/cleanup/`, `@cleanup_sandbox`, promotion's sweep) share that code and never delete the project. Room triggers (`trigger_*`/`v5_conditions.py`) read `room.db.triggers` as any `Sequence`/`Mapping` (`_SaverList`); `set_attribute` may write only identifier-shaped room Attributes (not `triggers`/`desc`) or `trigger_flag_*` on a character. Trigger types: `entry`/`exit` (room move hooks), `timed` (`RoomTriggerScript`, first fires one interval after the build), and `interaction` ("On Look", from `Room.at_desc`, which includes the look on arrival). There is no `.ev` export. The in-game counterparts are in `commands/builder/`.

**Help and news** are file-based (`docs/legacy-help/` is an unloaded archive). `world/help_entries.py` and `world/news_entries.py` load `world/help/<category>/*.{txt,yaml}` and `world/news/<category>/*.txt`; the file stem is the key and the directory the category. Command docstrings are help too, and a command beats a file entry with the same key (Evennia also ignores the `+`/`@` prefix), so long guides end in `-guide` (`roll-guide`, `hunger-guide`, `v5-rules-guide`, the single rules summary that the other guides point to). Staff-only entries are YAML with `locks: "read:perm(Builder);view:perm(Builder)"` (`world/help/staff/staff-approval.yaml`; `view` alone only hides it from the index). Write Evennia colour codes, not Markdown, and escape a literal `|` as `||`. Players read news as `news <category>` or `news <category>/<topic>`; `news` and the job commands (`jobs.cmdset.JobsCmdSet`) are on the `AccountCmdSet`, so they work before a player has an approved character and for staff without one. `tests/test_help_integrity.py` builds the cmdsets and fails if any help/news file or game-command docstring names a command, switch or topic that doesn't exist (by its real key: `roll`, not `+roll`), if a file key collides with a command, if Markdown is left, if a command added in `default_cmdsets.py` is shadowed, or if `disciplines_powers` disagrees with `v5_data`. It also checks locks: every command named in a help/news entry without a `perm(` lock must pass `cmd` access for a plain Player character, except the deliberate staff mentions in `PlayerLockTests.STAFF_MENTIONS`. A switch counts only if the command lists it in `switch_options` or compares a switch against it on a line mentioning `switch`.

**Migrations.** Always name the app (`evennia makemigrations traits`). A bare `makemigrations` can write proxy-model migrations into the installed Evennia package's own `objects` app. That has happened here before: app migrations once depended on a nonexistent `objects.0014`. Evennia's latest `objects` migration is `0013`.

**`web/website/VampSite/`** is a standalone static site (plain HTML/SCSS/JS, served outside Django; the `.shtml` error pages and `cgi-bin/` are for a traditional web host). Character creation happens on the game website: `index.html` and the two creation pages (`character-creation-new.html`, `character-creation.html`) only link to the game website's `/character-creation/` form (the game URL is set in one place; see its README). The old client-side builder JS (`assets/js/character-sheet*.js`) is no longer loaded but is kept. It also holds the owner's V5 reference PDFs. Django doesn't route to it, but it is not dead code, so don't delete it.
